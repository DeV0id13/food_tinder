# FoodTinder frontend — FT-06

Минимальный frontend первой итерации FoodTinder. Это SPA без UI-фреймворка: HTML, CSS,
vanilla JavaScript с ES modules и Vite как dev server/build tool. Backend API — единственный
источник аккаунта, рецептов, реакций, избранного, рационов и покупок.

## Возможности

- публичные лента и каталог рецептов, подробная карточка;
- регистрация без автоматического входа, отдельные login/logout;
- Django session cookie и CSRF для всех изменяющих запросов;
- «Нравится», «Не сегодня» и добавление в избранное как три независимых действия;
- избранное, загружаемое с backend;
- создание и выбор рационов на 1, 3 или 7 дней;
- выбор активных приёмов пищи: breakfast, lunch, snack, dinner;
- визуальный выбор и замена блюда по фотографии, поиск по совместимому избранному и 1–20 порций;
- отмена последнего свайпа;
- поиск и комбинируемые фильтры каталога;
- серверный чек-лист покупок с группами и прогрессом;
- прямые ссылки на разделы и восстановление каталога с фильтрами после обновления страницы;
- скачивание CSV/TXT из ответа backend с Blob и Content-Disposition;
- явные loading, empty, validation, auth/CSRF, not found, server и network states;

Приложение не хранит server state, пароль или session token в `localStorage`/`sessionStorage`.
Guest dislike живёт только в памяти открытой страницы. После перезагрузки приложение заново получает
сессию и данные с backend.

## Требования

- Node.js 22.12+ (подходит и Node.js 24);
- pnpm 11+;
- Django backend на `http://127.0.0.1:8000`;
- запуск frontend на `http://localhost:5173` или через [локальную сеть](#проверка-с-телефона).

Backend нужно подготовить из корня репозитория по корневому `README.md`: PostgreSQL,
миграции и заполнение каталога. В ветке `ft-06` подключены все модули FT-01…FT-05:
аккаунты, каталог, реакции, избранное, рационы, покупки и экспорт работают с настоящей
PostgreSQL. Покупки рассчитываются из сохранённого плана; отдельной копии списка в браузере нет.
Сетевые ошибки видны в интерфейсе.

## Установка

Из каталога `frontend/`:

```sh
pnpm install --frozen-lockfile
```

Версии frontend-зависимостей зафиксированы в `package.json` и `pnpm-lock.yaml`.
Если pnpm не установлен глобально: `npx --yes pnpm@11 install --frozen-lockfile`.
После установки команды scripts доступны и через npm: `npm run dev`, `npm test`,
`npm run test:integration`, `npm run lint`, `npm run build`.

## Django API

1. Запустить Django на `http://127.0.0.1:8000`.
2. В `frontend/` выполнить:

   ```sh
   pnpm dev
   ```

3. Открыть `http://localhost:5173/`.


### Подготовка настоящего backend

С Docker из корня репозитория (предварительно создать `.env` по корневому README):

```sh
docker compose build web
docker compose up -d --wait postgres
docker compose run --rm web python manage.py migrate
docker compose up -d web
```

Если Django запускается на хосте, нужны Python 3.12+, PostgreSQL 16+, виртуальное окружение
с `pip >= 25.1` и зависимости `python -m pip install --group dev`. Передайте переменные
из `.env` в окружение процесса; Django сам этот файл не читает. Укажите `POSTGRES_HOST=127.0.0.1`
и реальный порт локальной БД (вместо Compose hostname `postgres`), затем выполните:

```sh
python manage.py migrate
python manage.py runserver 127.0.0.1:8000
```

Порядок ручной проверки после заполнения каталога:
гостевой каталог → регистрация → отдельный вход → избранное и реакции → рацион → покупки
и CSV/TXT. После reload или входа тем же аккаунтом в другом браузере избранное, реакции,
планы и порции загружаются из PostgreSQL. Рационы запрашиваются при открытии соответствующего
раздела. Локальная база сохраняется в Docker volume после перезапуска контейнеров.
Старый frontend на порту 4173 не нужен: для совместной работы открывайте `localhost:5173`.

### Dev proxy и CSRF

Vite проксирует `/api/` на `http://127.0.0.1:8000`:

```js
proxy: {
  '/api': {
    target: 'http://127.0.0.1:8000',
    changeOrigin: false,
  },
}
```

Так браузер работает с одним origin `localhost:5173`, а proxy сохраняет исходный Host.
Отключать Django CSRF или менять CORS не нужно.

При старте клиент вызывает `GET /api/v1/auth/session/`, получает cookie `csrftoken`, читает
её непосредственно перед unsafe request и отправляет `X-CSRFToken`. Все запросы используют
`credentials: "include"`. После login клиент повторно вызывает session endpoint, потому что
Django ротирует CSRF token.

### Проверка с телефона

Подключите компьютер и телефон к одной локальной сети. Подготовьте локальный `.env`
по корневому README, запустите Docker и установите frontend-зависимости. Остановите
предыдущий Vite на порту 5173. Затем из корня репозитория выполните команду.

```sh
docker compose build web
./frontend/dev-lan.sh
```

Скрипт определяет IPv4 компьютера по маршруту по умолчанию. Если этот маршрут идёт
через VPN, передайте IPv4 интерфейса Wi-Fi вручную, например `./frontend/dev-lan.sh start 192.168.1.42`.

Скрипт запускает PostgreSQL и Django в существующем проекте Docker Compose, применяет
миграции и открывает Vite на порту 5173 для локальной сети. Откройте на телефоне URL,
напечатанный в терминале.
Команда сборки нужна при первом запуске или после изменений Dockerfile.
Заполнить начальный каталог можно вместе с [фотографиями](#фотографии-рецептов).

Для Django сохраняется привязка `127.0.0.1:8000`, а браузер обращается к `/api/` и `/media/` на
том же адресе, что и к интерфейсу. Vite передаёт исходный `Host`, поэтому Django
проверяет тот же `Origin` и выдаёт сессионные и CSRF cookies для адреса, открытого
в браузере. Если IP ещё отсутствует в `DJANGO_ALLOWED_HOSTS`, скрипт добавляет его
через дополнительный Compose-файл для этого запуска. `.env` сохраняется без изменений.

Для фонового запуска выполните из корня репозитория следующую команду.

```sh
nohup ./frontend/dev-lan.sh start > frontend/node_modules/.foodtinder-lan.log 2>&1 &
```

Адрес для телефона появится в журнале `frontend/node_modules/.foodtinder-lan.log`.
При обычном запуске `Ctrl+C` завершает Vite. Команда `./frontend/dev-lan.sh stop`
завершает Vite, запущенный этим скриптом, и останавливает контейнеры проекта с
сохранением томов PostgreSQL и фотографий.

### Каталог и фотографии

Создавайте рецепты через Django Admin на `http://localhost:8000/admin/` или используйте
[импорт подготовленного каталога](../docs/modules/catalog.md#импорт-каталога).
Создание и замена фотографий выполняются в поле Photo. URL `/media/recipes/…` выдаёт
Django. На MacBook Vite проксирует их на том же origin, что и API.

## Команды

```sh
pnpm dev          # Vite dev server, localhost:5173, proxy /api/
pnpm test         # Node test runner
pnpm run test:integration # live smoke через Vite + Django + PostgreSQL
pnpm lint         # синтаксическая проверка критичных JS-модулей
pnpm build        # production build в frontend/dist/
pnpm preview      # просмотр готового build на localhost:4173
```

`dist/` и `node_modules/` игнорируются Git.

`pnpm run test:integration` требует работающих Django, PostgreSQL, Vite и каталога рецептов.
Проверка использует настоящие `ApiClient`/`RealApi`, cookies и CSRF через `localhost:5173`,
создаёт избранное и планы 1/3/7, меняет порции, получает покупки и CSV/TXT, затем входит
тем же аккаунтом с независимыми cookies и проверяет сохранённые данные. Созданные проверкой
планы удаляются; случайный аккаунт `ft06-smoke-…@example.test` с тестовым лайком остаётся
в локальной базе. Пользовательские записи не затрагиваются. Запускайте только на dev-базе.
Для другого локального порта задайте `FOODTINDER_ORIGIN`; внешние хосты запрещены.

Регрессионные проверки контроллера находятся в `tests/app-state.test.mjs`: ответы двух
рационов/покупок в обратном порядке, поздние ошибки, смена аккаунта и logout с сетевой
ошибкой последующего session request. Интеграция готовых серверных маршрутов проверяется
`pytest tests/test_frontend_integration.py` на PostgreSQL (с загруженным окружением backend).
Проверка покрывает также рационы, порции, покупки, оба формата экспорта и восстановление
данных после нового входа.

## Ручная проверка

1. Запустить PostgreSQL и Django, применить миграции и создать или импортировать рецепты.
2. Запустить `pnpm dev`, открыть `http://localhost:5173/`.
3. Убедиться, что лента показывает рецепты из PostgreSQL.
4. Как гость открыть «Лента» и «Рецепты», открыть подробности рецепта.
5. Нажать «Нравится»: должен открыться экран входа, server state не меняется.
6. Вернуться в ленту и нажать «Не сегодня»: карточка скрывается только до reload.
7. Зарегистрировать новый email и валидный пароль. Убедиться, что UI предлагает войти и
   пользователь всё ещё гость.
8. Войти. В DevTools проверить session cookie; пароль и токены не должны появиться в storage.
9. Нажать кнопку с закладкой. Карточка остаётся на месте, а рецепт появляется в «Избранном».
10. Нажать «Нравится». Должна появиться следующая карточка в ленте.
11. На другой карточке нажать «Не сегодня» и проверить следующую актуальную карточку.
12. Добавить в избранное минимум по одному совместимому рецепту для нужных meal types.
13. Открыть «Рационы», создать планы на 1, 3 и 7 дней с разными enabled meals.
14. Переключить активный сохранённый план в select.
15. В плане на 1 день открыть «Выбрать блюдо» и выбрать карточку совместимого рецепта.
16. Изменить servings, сохранить и reload страницы: слот и порции должны прийти с backend.
17. Заменить рецепт в слоте другим совместимым favorite recipe.
18. Удалить слот; повторное удаление допустимого пустого слота не должно ломать UI.
19. Открыть «Покупки», выбрать план и сверить ingredient name, quantity, unit.
20. Отметить продукт и обновить страницу. Проверить отметку, затем изменить порции рецепта и
    убедиться, что изменившееся количество больше не отмечено купленным.
21. Скачать CSV и TXT. Проверить имена из `Content-Disposition` и содержимое backend-файлов.
22. Удалить план и убедиться, что он исчез из select.
23. Выйти; приватные экраны должны предлагать вход, публичный каталог остаётся доступен.
24. Войти снова/в другом браузере и проверить восстановление favorites и meal plans с backend.
25. Остановить backend, повторить запрос и убедиться, что интерфейс показывает ошибку и кнопку повтора.
26. Проверить 400 на невалидной форме, 403/expired session и 404 удалённого плана: UI должен
   показывать ошибку и не изображать успешное действие.

## Ограничения первой итерации

Нет drag-and-drop, автозаполнения рациона, профиля, undo, истории свайпов, суммарных КБЖУ,
бюджета. Количества и файлы экспорта рассчитывает Django.
Production deployment и reverse proxy не входят в FT-06.
