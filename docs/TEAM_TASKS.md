# FoodTinder — шесть задач для первого командного этапа

Основа: `master` на commit `3962480c32e2d905788beb38a408b4b9ec600415`, проверено 20.09.2026.
Общий контракт — [ITERATION_1_CONTRACT.md](ITERATION_1_CONTRACT.md).
Каждый раздел FT-01…FT-06 можно перенести в отдельный GitHub Issue.

## Что получится

Рабочий сценарий: аккаунт → каталог и реакции → избранное → ручной рацион → покупки и экспорт.
Это первая итерация, а не весь FoodTinder. Сложные расширения перечислены в контракте.
CI/CD и настройки автоматического запуска проверок девопс добавляет позже.

Шесть задач распределены по зонам кода: пять backend-модулей и один минимальный frontend.
Это распределение работы, а не предположение о специальностях участников. Девопс может
быть одним из шести исполнителей; его последующая задача по CI/CD в эти шесть не включена.
Имена исполнителей команда назначает перед стартом. Интегратор — один из этих же шести человек.

| --- | --- | --- | --- |
| FT-01 | `apps/accounts/**`, `tests/accounts/**` | `docs/modules/accounts.md` | `feat/ft-01-accounts` |
| FT-02 | `apps/catalog/**`, `tests/catalog/**` | `docs/modules/catalog.md` | `feat/ft-02-catalog` |

| FT-06 | `frontend/**` (включая свои тесты и package lock) | `docs/modules/frontend.md` | `feat/ft-06-frontend` |

`**` включает модели, serializers, views, urls, migrations, admin, локальные helpers и fixtures.
Документы в последнем столбце путей создаёт только владелец соответствующего модуля.
В `tests/<module>/conftest.py` разрешены собственные фикстуры; не выносить их в корневой conftest.
Разрешено создавать тестовые данные чужих моделей в своей тестовой БД по контракту,
но не менять чужие models.py, migrations, fixtures или импортировать чужие тестовые helpers.

За интегратором закреплены все общие пути: `config/**`, `common/**`, корневой `README.md`,
`AGENTS.md`, этот документ и контракт, `pyproject.toml`, `Dockerfile`,
`compose.yaml`, `docker/**`, `.env.example`, `.gitignore`, существующие корневые тесты,
`tests/conftest.py`, `tests/__init__.py`. Новые общие пути также сначала обсуждаются с ним.
`.github/**` зарезервирован для последующей работы девопса.

Интегратор вносит общие правки в отдельной ветке после обновления от master, по очереди,
а не внутри нескольких параллельных feature-веток. Не расширяйте allowlist задачи самовольно.

Раздельные файлы устраняют плановые текстовые пересечения. Абсолютную гарантию отсутствия
любых Git-конфликтов дать нельзя: она нарушается, например, переименованием чужих файлов
или одновременной правкой общего контракта. Семантическая совместимость обеспечивается
контрактом и интеграционными проверками; одних разных каталогов недостаточно.

## Подготовка до старта шести задач

Это общий организационный шаг, а не седьмая продуктовая задача.

1. Интегратор кладёт `AGENTS.md` в корень, этот файл и контракт — в `docs/` и проводит
   небольшой подготовительный PR. Команда фиксирует договорённости до написания моделей.
2. Назначает исполнителей и себя как единственного владельца общих файлов.
3. Передаёт владельцу FT-06 уже подготовленный архив `FoodTinder-source.zip` как визуальную
   основу. Он самостоятельно переносит необходимые материалы только в `frontend/`.
4. Все создают свои ветки от одного обновлённого `master`. Никаких параллельных коммитов
   нескольких человек в `feat/stage_one`.

Заглушки чужих моделей и пустые миграции ради старта не добавляются. Все приложения уже
зарегистрированы в INSTALLED_APPS. Автоматизацию, новые зависимости и инфраструктуру
для этого документа создавать не нужно.

## FT-01 — регистрация, сессия и базовый профиль

**Результат:** новый пользователь создаёт аккаунт, входит по email, выходит и читает/меняет
собственный базовый профиль через API. Существующая Admin-аутентификация сохраняется.

**Делать только в:** зоне FT-01 из таблицы. `config/urls.py` уже подключает accounts;
корневые настройки и существующие foundation-тесты не редактировать.

**Объём работы:**

1. Добавить register/login/logout и GET/PATCH profile по разделу FT-01 контракта.
2. Сохранить формат и CSRF-инициализацию существующего auth/session.
3. Регистрацию пользователя и профиля сделать атомарной; использовать существующий
   UserManager, валидаторы пароля и механизм хеширования Django.
4. Учесть повторный email в другом регистре, включая конфликт ограничения БД.
5. Защитить анонимные login/register POST от CSRF; реализовать корректное завершение сессии.
6. Предоставить профиль только владельцу и явно обрабатывать старый аккаунт без профиля.

**Приёмка:**

- Корректная регистрация возвращает 201; session остаётся гостевой до явного login.
- Email с другим регистром не создаёт второй аккаунт; неверный пароль регистрации даёт 400.
- Login/password с верными данными создаёт сессию, неверные данные возвращают общую ошибку.
- Anonymous POST без CSRF на register/login отвергается, а с корректным токеном проходит.
  Проверки выполняются с `APIClient(enforce_csrf_checks=True)`.
- Logout делает последующий session анонимным; повторный logout с корректным CSRF безопасен.
- Профиль A не раскрывается B; отрицательный вес/рост и будущая дата рождения отвергаются.
- Существующий auth/session и Admin продолжают работать; новые тесты — `tests/accounts/`.

**Зависимости:** только уже существующий backend. Можно завершить независимо от остальных.
**Не входит:** письма, капча, восстановление пароля, смена email, аватары, медицинская анкета, UI.

## FT-02 — каталог, состав рецептов и демонстрационные данные

**Результат:** гостю и вошедшему пользователю доступны реальные карточки с составом и шагами,
а остальные backend-модули могут ссылаться на согласованные модели рецепта и ингредиента.

**Делать только в:** зоне FT-02. Миграции — `apps/catalog/migrations/`; общих fixtures не создавать.

**Объём работы:**

1. Реализовать Ingredient, Recipe, RecipeIngredient и ограничения из контракта.
2. Добавить админку с редактированием состава и проверкой возможности публикации.
3. Реализовать публичные GET recipes/ и recipes/<id>/, локальную пагинацию и документированные DTO.
4. Сделать идемпотентную команду `python manage.py seed_demo_recipes`: минимум 12 рецептов,
   все четыре типа приёма пищи, минимум три общих ингредиента между рецептами.
5. Добавить контрольные A/B из контракта с постоянными slug `demo-rice-chicken` и
   `demo-rice-milk`; ID получать из БД. Повтор команды не создаёт дубликатов и не
   перезаписывает вручную изменённые записи; никаких пользователей/паролей она не создаёт.
6. Предоставить `apps/catalog/urls.py`; нужный корневой include описать в своём документе.

**Приёмка:**

- Миграции применяются поверх текущего scaffold в PostgreSQL.
- Гость получает активные карточки и детали; неактивные рецепты не видны через list/detail.
- У активного рецепта есть состав, шаги и непустой список допустимых приёмов пищи.
- Отрицательные/нулевые количества и повтор одного ингредиента в рецепте отвергаются;
  единица существующего используемого ингредиента не меняется.
- Количество в detail относится к base_servings и передаётся Decimal-строкой.
- После двух запусков seed число демонстрационных рецептов не удваивается.
- Тесты моделей, API и seed находятся в `tests/catalog/`.

**Зависимости:** только существующий backend. Желательно слить раньше других доменных задач.
**Не входит:** лента с личными исключениями, реакции, теги/поиск/сложные фильтры,
загрузка фотографий, парсинг сайтов, публикация рецептов пользователями, расчёт нутриентов.

## FT-03 — лайки, суточные дизлайки, избранное и лента

**Результат:** пользователь сохраняет разные типы предпочтений, видит свою ленту и избранное;
другие аккаунты имеют независимые состояния.

**Делать только в:** зоне FT-03. Catalog читать по контракту, его сериализаторы и модели не менять.

**Объём работы:**

1. Реализовать UserRecipeState и unique `(user, recipe)`.
2. Реализовать feed, swipes, favorites list и PUT favorite по контракту.
3. Считать dislike активным только до следующей полуночи UTC, без очередей и очистки по cron.
4. Сохранить различие между liked_at и is_favorite; лайк не добавляет избранное автоматически.
5. Предоставить `is_favorite` в собственном selectors.py для FT-04.
6. Собирать RecipeSummary из согласованных полей каталога, не дополняя catalog личными полями.

**Приёмка:**

- Like переживает смену суток; dislike до полуночи скрывает рецепт, после неё перестаёт скрывать.
- Повторный like не меняет первое liked_at; повторный favorite не создаёт вторую запись.
- Удаление из избранного сохраняет лайк; like после dislike снимает активный dislike.
- Лента A учитывает состояния A, не B; пустая лента возвращает 200 с пустым results.
- Гость читает feed, но не сохраняет реакции; action=skip и неизвестные действия отвергаются.
- Неактивный рецепт не добавляется в избранное, но старую отметку можно снять.
- Проверки границы суток управляют временем в тесте, а не ждут настоящую полночь.

**Зависимости:** модели и миграция FT-02 для проверки с БД. Новая регистрация FT-01 не блокирует
тесты: существующий UserManager уже позволяет создавать пользователей для APIClient.
До слияния FT-02 можно реализовать обработку времени/состояний и подготовить тестовые сценарии.
**Не входит:** ML-рекомендации, нейтральный свайп, undo, история всех событий, timezone пользователя,
Redis, guest-состояния на сервере и frontend.

## FT-04 — ручной конструктор рациона

**Результат:** пользователь создаёт план на 1/3/7 дней, добавляет в допустимые слоты блюда
из своего избранного, меняет порции и удаляет блюда/планы.

**Делать только в:** зоне FT-04. Модели catalog и selector preferences использовать без правок.

**Объём работы:**

1. Создать MealPlan, MealPlanSlot и ограничения из контракта.
2. Реализовать список, создание, получение и удаление своих планов.
3. Реализовать PUT/DELETE конкретного слота: один рецепт и 1–20 порций на слот.
4. Проверять владельца, границы периода, enabled_meals, совместимость meal_type рецепта
   и наличие нового/заменяемого рецепта в избранном.
5. Удерживать существующее блюдо после удаления из избранного; разрешать изменение его порций.
6. Предоставить `get_plan_for_user` в selectors.py для покупок.

**Приёмка:**

- Создаются планы на 1, 3, 7 дней; duration=2 и пустой enabled_meals отвергаются.
- Нельзя заполнить день вне периода, выключенный слот или завтрак рецептом только для ужина.
- Нельзя добавить чужой/неизбранный рецепт в обход UI; владельцем всегда становится request.user.
- Повторный PUT обновляет тот же слот; уникальность защищена БД, при одновременных
  валидных PUT не возникает дубликатов (допустима семантика «последняя запись побеждает»).
- После удаления recipe из favorites сохранённый слот остаётся и его порции редактируются.
- Пользователь B получает 404 на план A и его вложенные операции.
- Смена порций и удаление слота видны при повторном GET; перезапуск backend не теряет план.

**Зависимости:** FT-02 и FT-03. До их слияния можно писать валидацию периода/слотов и тесты
на локальных mock-объектах; окончательные миграции и тесты БД — на реальных зависимостях.
**Не входит:** автоподбор, перенос периода существующего плана, drag-and-drop,
КБЖУ/стоимость всего плана, формирование покупок и UI.

## FT-05 — расчёт списка покупок и экспорт CSV/TXT

**Результат:** любой собственный сохранённый план превращается в суммарные количества
ингредиентов; один и тот же результат доступен как JSON, CSV и TXT.

**Делать только в:** зоне FT-05. Новые таблицы не нужны. Planning/catalog только читать.

**Объём работы:**

1. Реализовать чистую функцию агрегации состава с учётом base_servings и slot.servings.
2. Через `get_plan_for_user` проверять владельца, затем получать состав запланированных рецептов.
3. Группировать по ingredient.id и рассчитывать Decimal до финального округления.
4. Добавить shopping-list и export endpoints, Content-Type и Content-Disposition.
5. Обрабатывать пустой план и экранировать CSV; не дублировать расчёт в экспортёрах.

**Приёмка:**

- Контрольный пример из контракта даёт 400 g риса, 450 g курицы, 200 ml молока.
- После изменения порций и удаления слота следующий запрос даёт новые значения.
- Нет потери точности из-за float и промежуточного округления по каждой строке.
- Один Ingredient, встретившийся в нескольких днях, присутствует в результате одной строкой.
- Пустой план и неизвестный file_type обрабатываются по контракту.
- JSON/CSV/TXT содержат одинаковые количества; имена с `;`, кавычками и формулами
  не ломают CSV и не выполняются как формулы после открытия в таблице.
- Пользователь B не получает покупки и файл экспорта из плана A.

**Зависимости:** FT-02 и FT-04 для ORM/API-тестов. Расчёт и экспорт можно начать сразу
на собственных локальных тестовых данных; затем проверить на реальных моделях.
**Не входит:** отметки «куплено», ручные товары, объединение нескольких планов,
цены магазинов, стоимость корзины, упаковки, фоновые задачи и UI.

## FT-06 — минимальный frontend для общего сценария

**Результат:** весь этап можно пройти в браузере без Swagger, Django Admin или ручных HTTP-запросов.
Ориентир — уже созданный FoodTinder-прототип; сложную бизнес-логику перенести в API.

**Делать только в:** `frontend/**` и `docs/modules/frontend.md`. Backend, root package files,
Docker, CORS/settings и reverse proxy production не редактировать.

**Объём работы:**

1. Переиспользовать HTML/CSS/изображения прототипа там, где это экономит работу.
   Сохранить простой HTML/CSS/JavaScript подход; React и переписывание дизайна не нужны.
2. Сделать один API-клиент с обработкой cookies, CSRF, ошибок и загрузки. После login
   перечитывать csrftoken; пароль/токен сессии в localStorage не сохранять.
3. Экраны: вход/регистрация; карточка с кнопками «Нравится», «Не сегодня», «В избранное»;
   избранное; ручной план; покупки с экспортом. Кнопки достаточны для первой итерации.
4. План: создать на 1/3/7 дней, выбрать активные приёмы пищи, выбрать сохранённый план,
   добавить рецепт через список, изменить порции, удалить слот. Без drag-and-drop.
5. Гостю показать каталог; сохранение реакций предлагает вход. Гостевой dislike может
   убрать текущую карточку только в памяти страницы, без фиктивной записи на сервере.
6. Предоставить состояния loading/empty/error и обновлять UI после успешного ответа API;
   при ошибке не показывать действие как успешно сохранённое.
7. Пока backend не готов, использовать явный demo/mock-режим по контракту внутри frontend.
   Переключение на него при ошибке реального API запрещено: ошибка должна быть видна.
8. Настроить локальный dev proxy `/api/` на `http://127.0.0.1:8000`, сохраняя исходный
   Host (`changeOrigin: false`); открывать frontend через localhost. При необходимости
   использовать Vite только как dev server/build tool; package.json и lock — внутри frontend.
   Backend в Docker остаётся доступен через опубликованный порт 8000.
9. Описать запуск и проверки в `frontend/README.md`. Указать разделение запуска на хосте
   и в контейнере, если потребуется другой адрес прокси; не менять общий Compose.

**Приёмка:**

- После регистрации пользователь явно входит; session и CSRF работают через dev proxy.
- Лайк и избранное визуально разные; после лайка/дизлайка показывается следующая карточка;
  star переключает избранное, не является нейтральным свайпом и не убирает карточку.
- Можно создать план, добавить совместимый рецепт из избранного, изменить servings,
  увидеть пересчитанные покупки и скачать CSV/TXT.
- После reload и после входа тем же аккаунтом в другом браузере видны серверные данные.
- При истечении сессии UI предлагает вход, при сетевой ошибке показывает ошибку;
  настоящий API не подменяется незаметно локальными данными.
- Интерфейс пригоден при desktop-ширине 1280 px; есть понятные пустые состояния.
- Описана и выполнена ручная проверка полного сценария на настоящем backend.
  Проверки API-клиента/критичных UI-операций, если добавлены, лежат в frontend.

**Зависимости:** можно начать сразу по контракту и мокам. Готовность всей задачи требует
FT-01…FT-05 и подключённых интегратором маршрутов. Прототип с localStorage не считается интеграцией.
**Не входит:** экран расширенного профиля, весь функционал старого прототипа,
новый дизайн, мобильное приложение, деплой и публичное размещение.

1. Подготовительный PR с тремя документами.
2. FT-01 и FT-02 — независимые PR, любой порядок. FT-02 раньше разблокирует доменные задачи.
3. FT-03 после FT-02; FT-04 после FT-03; FT-05 после FT-04.
4. FT-06 можно разрабатывать с первого дня; его финальная интеграционная проверка — после backend.

Внутри этого порядка можно ревьюить draft PR заранее. Разработка параллельная, завершение
зависимых тестов последовательное. Мы не обещаем шесть полностью независимых backend-функций.
Ветки обновляются от master после слияния зависимостей; не копировать чужой код и миграции
через cherry-pick и не создавать поддельные модели в production-каталогах.

Интегратор после готовности каждого модуля подключает единственный новый include в `config/urls.py`:

| Префикс | URLConf | Когда |
| --- | --- | --- |
| `api/v1/auth/` | `apps.accounts.urls` | уже существует |
| `api/v1/recipes/` | `apps.catalog.urls` | после FT-02 |
| `api/v1/preferences/` | `apps.preferences.urls` | после FT-03 |
| `api/v1/meal-plans/` | `apps.planning.urls` | после FT-04 |
| `api/v1/shopping-list/` | `apps.shopping.urls` | после FT-05 |

До этого автор может подключить URLConf своего приложения через `tests/<module>/urls.py`
и локальный `settings.ROOT_URLCONF` для теста, сохранив используемые существующие auth routes.
Не переопределять глобальный tests/conftest.py и не регистрировать незавершённые модули в config.

Каждый автор генерирует миграции только своего app после появления реальных зависимостей.
Одинаковое имя `0001_initial.py` в разных apps не является конфликтом. Уже слитые миграции
не перенумеровываются; межмодульные FK dependencies указывают настоящие имена миграций.
Ни catalog, ни preferences, ни planning не должны получить обратную зависимость от shopping.

Локальная готовность PR: проверки из AGENTS.md, актуальная ветка, соответствие контракту,
описание интеграционных подключений и честный список ещё не выполненных проверок.
После интеграции — полный pytest с PostgreSQL, проверка миграций и сквозной пример контракта.
Отсутствие GitHub Actions сейчас не отменяет локальную проверку.

## Короткий промпт исполнителю для Codex

> Прочитай AGENTS.md, docs/ITERATION_1_CONTRACT.md и задачу FT-XX в docs/TEAM_TASKS.md.
> Реализуй только эту задачу в отдельной ветке. Соблюдай разрешённые пути, модели и API.
> Не меняй общие файлы и чужие модули; интеграционные потребности запиши в документе своего модуля.
> Проверь критерии приёмки доступными средствами. Если зависимость ещё не слита,
> выполни независимую часть и явно перечисли оставшиеся проверки. CI/CD не добавляй.
> В конце покажи изменённые файлы, результаты проверок и оставшиеся ограничения.
