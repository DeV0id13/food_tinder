# FT-02 — каталог рецептов

## Модели и ограничения

- `Ingredient`: уникальный `slug`, название и каноническая единица `g`, `ml` или `pcs`. Используемый ингредиент защищён от удаления (`PROTECT`), а его единица не меняется через модель или Admin.
- `Recipe`: уникальный `slug`, карточка, время приготовления, сложность 1–5, базовое число порций, непустые массивы `meal_types` и `steps`, флаг активности. Пять необязательных показателей на порцию — `Decimal(10,2)` с неотрицательными значениями; `null` означает неизвестное значение. Они не вычисляются из состава.
- `RecipeIngredient`: связь рецепта с ингредиентом, уникальная пара и положительное `Decimal(12,3)` количество на **весь** рецепт с `base_servings` порциями. Для `pcs` количество целое. Простые инварианты подкреплены ограничениями PostgreSQL, правила JSON и `pcs` проверяются моделью.

## Admin

Ингредиенты и рецепты редактируются в Django Admin; строки состава — inline рецепта. Неактивный рецепт может оставаться без состава. Для активного рецепта formset проверяет итоговые inline-строки с учётом добавления и удаления, поэтому создание рецепта вместе с первой строкой допускается, а публикация без строк отвергается.

Поле `Photo` в карточке рецепта в Admin принимает статичные JPEG, PNG и WebP до 10 МБ и 24 Мп. Файл можно заменить или снять флажком `Clear`. При замене или очистке прежний файл удаляется после сохранения рецепта. При наличии загруженной фотографии она используется первой. Поле `Image url` остаётся для ранее сохранённых внешних ссылок.

## Публичный API

Оба endpoint доступны гостю и вошедшему пользователю; клиентское редактирование каталога отсутствует.

| Метод | Путь | Результат |
| --- | --- | --- |
| GET | `/api/v1/recipes/` | Активные рецепты, `id` по возрастанию, страница `count/next/previous/results` |
| GET | `/api/v1/recipes/<recipe_id>/` | Активный рецепт с шагами и составом; неактивный/неизвестный ID даёт 404 |

Локальная `LimitOffsetPagination`: `limit=30` по умолчанию, максимум 100, `offset=0`. `RecipeSummary` содержит только `id`, `title`, `image_url`, `cooking_time_minutes`, `difficulty`, `base_servings`, `meal_types` и пять справочных показателей на порцию. `RecipeDetail` добавляет `description`, `steps` и `ingredients`; строка состава содержит только `ingredient_id`, `name`, `unit`, `quantity`. Decimal передаётся строкой с точкой; `quantity` всегда с тремя знаками. `slug` и `is_active` в DTO отсутствуют.

Для загруженного файла `image_url` содержит путь `/media/recipes/…`. Лента и избранное используют тот же сериализатор, что и каталог.

## Импорт каталога

Положите проверенные фотографии в каталог `catalog-import/photos/` под именами,
указанными в [манифесте](../catalog/recipes.json). Файлы в `catalog-import/` остаются вне Git.
Команда использует локальные файлы с проверкой фактического формата. Она не скачивает
изображения из ссылок на авторов и лицензии.

```sh
docker compose exec web python manage.py import_catalog \
  --manifest docs/catalog/recipes.json --media-dir catalog-import --dry-run
docker compose exec web python manage.py import_catalog \
  --manifest docs/catalog/recipes.json --media-dir catalog-import
```

Рецепты сопоставляются по slug или существующему названию. Команда сохраняет первичные
ключи, связи и уже загруженные фотографии. Редакционные обновления применяются только
к записям, чьи прежние описание, шаги и время совпадают с проверенной версией в манифесте.
Каждый рецепт импортируется отдельной транзакцией. После частичного сбоя исправьте строки
из отчёта и запустите команду повторно. Импорт требует доступа к management command.

В существующий каталог перенесены 50 новых рецептов и 46 фотографий. Молочная рисовая
каша и треска с картофелем сопоставлены с существующими рецептами. У горохового супа
с овощами фотография оставлена в архиве из-за мясной добавки на снимке. Исходные 49
снимков сохранены в локальном `catalog-import/demo/`, включая альтернативные.
У трёх других рецептов фотографий в исходных данных не было. За редакционную атрибуцию
отвечают манифест и страница «Авторы фотографий».

## Хранилище

PostgreSQL 16 хранит данные в `postgres_data`. Django хранит ключи фотографий в базе,
а сами изображения — в постоянном томе `recipe_photos` по пути
`/app/media/recipes`. Админка и импорт используют один backend Django Storage.
Локальный файловый том подходит для одного приложения и сохраняется при пересоздании
контейнера. Локальная выдача использует относительный `/media/` через Vite.

Для будущего S3-совместимого размещения установите адаптер хранилища в образ и задайте
`DJANGO_MEDIA_STORAGE_BACKEND` (путь к классу) и `DJANGO_MEDIA_STORAGE_OPTIONS`
(JSON-объект настроек) в окружении. Объекты перед переключением нужно скопировать с теми
же ключами. Передавайте доступы через окружение и выдавайте браузеру адреса для чтения,
доступные из его сети.

## Проверки

`python manage.py migrate`, `python manage.py makemigrations --check --dry-run`,
`python manage.py check` и `pytest tests/catalog` выполняются с PostgreSQL.


Выдача списка использует общий `StandardPagination` с лимитом 30 по умолчанию
и максимумом 100. `catalog.selectors.get_recipe` возвращает активный рецепт
для новых назначений в рацион и свайпов. Снятие закладки допускает также
неактивный рецепт.
