# FT-01 — accounts

Маршруты уже подключены через `config/urls.py` по префиксу `/api/v1/auth/`.
Дополнительных подключений интегратору не требуется.

| Метод | Путь | Поведение |
| --- | --- | --- |
| GET | `session/` | Текущий `{authenticated, id, email}`; устанавливает CSRF cookie. |
| POST | `register/` | Проверяет имя, email и пароль, атомарно создаёт User и UserProfile, возвращает 201 `{id, email, first_name}` без входа. |
| POST | `login/` | Проверяет email/пароль через Django, создаёт сессию, возвращает 200 `{authenticated, id, email}`. |
| POST | `logout/` | Завершает сессию, возвращает 204 также для гостя. |
| GET | `profile/` | Возвращает только базовые поля своего профиля. |
| PATCH | `profile/` | Частично меняет только базовые поля своего профиля и возвращает полный профиль. |

Используются Django session cookie и DRF `SessionAuthentication`. Для каждого
`register/login/logout` явно вызывается стандартная проверка CSRF из
`SessionAuthentication`, включая анонимные запросы. Клиент получает `csrftoken`
через `GET session/` и передаёт актуальный токен в `X-CSRFToken`. После login Django
ротирует CSRF token, поэтому клиент перечитывает cookie. Приватные ответы и
ответ сессии помечены `never_cache`.

Email нормализуется существующим `UserManager`; повтор без учёта регистра
возвращает 400 по `email`, включая конфликт ограничения БД. Перед созданием
пользователя применяется Django `validate_password`; пароль хранится штатным
хешированием Django. Неверные учётные данные при входе возвращают одинаковую
ошибку `non_field_errors`.

Профиль содержит только `date_of_birth`, `gender`, `height_cm`, `weight_kg`.
Дата рождения не может быть в будущем, пол ограничен существующими choices и
пустой строкой, рост и вес должны быть положительными и помещаться в поля модели.
Неизвестные и запрещённые поля записи дают 400. Decimal выдаётся строкой.
Если у старого пользователя нет UserProfile, GET возвращает пустые значения без
создания записи; PATCH создаёт запись и применяет изменения.

## FT-11: данные аккаунта

Доступные поля `User` включают `first_name` и `last_name` (унаследованы от Django AbstractUser):
миграция для новых полей не нужна.

- `POST /api/v1/auth/register/`: `first_name` обязателен; имя должно быть непустым
  после удаления пробелов и не длиннее 150 символов. Возвращает `id, email, first_name`.
  Новый пользователь **не входит автоматически**.
- `GET /api/v1/auth/account/`: данные текущего пользователя:
  `{first_name, last_name, email}`. Не требует отдельного UserProfile.
- `PATCH /api/v1/auth/account/`: принимает только `first_name` и `last_name`,
  обновляет их у текущего пользователя.
- `POST /api/v1/auth/account/email/`: принимает `email` и `current_password`;
  обязательно проверяет текущий пароль, валидность адреса и
  регистронезависимую уникальность. БД защищает от гонок.
  Сессия остаётся действующей, следующий вход — по новому email.
- Все новые endpoint приватные, запросы записи требуют стандартный CSRF,
  неизвестные поля отклоняются. Пароли никогда не возвращаются.

**Ограничение:** отправка письма для подтверждения нового email пока не настроена.
Новый адрес может быть ошибочным; следует добавить подтверждение по токену и
настроить SMTP до эксплуатации в публичном сервисе. Пока сайт работает по HTTP,
вводить реальный пароль не следует: для аккаунтов нужен HTTPS.

Поля профиля `date_of_birth`, `gender`, `height_cm`, `weight_kg`
по-прежнему доступны отдельно через старый `/profile/` без изменения контракта.


## Лимиты авторизации

API входа, API регистрации и `POST /admin/login/` расходуют отдельные лимиты
по адресу источника после проверки CSRF, включая запросы с ошибками валидации.
Django Admin сохраняет стандартную форму, проверку прав staff и сессии.
Все настройки опциональны:

| Переменная | По умолчанию |
| --- | --- |
| `AUTH_LOGIN_LIMIT` | 20 попыток |
| `AUTH_LOGIN_WINDOW_SECONDS` | 60 секунд |
| `AUTH_REGISTER_LIMIT` | 10 попыток |
| `AUTH_REGISTER_WINDOW_SECONDS` | 300 секунд |
| `AUTH_ADMIN_LOGIN_LIMIT` | 20 попыток |
| `AUTH_ADMIN_LOGIN_WINDOW_SECONDS` | 60 секунд |

Более короткое окно входа учитывает обычные повторы и общий IP у пользователей
за NAT. Более длинное окно регистрации сдерживает частое создание аккаунтов.
Окно начинается с первого запроса операции. При превышении API и Admin
возвращают 429 и `Retry-After` в секундах. Frontend входа и регистрации
показывает время ожидания при корректном заголовке. Email не участвует в ключе, поэтому адрес аккаунта
не блокируется из-за запросов с другого IP. Пользователи за одним NAT делят
лимит. IP берётся из `REMOTE_ADDR` или из перезаписанного Caddy заголовка в
закрытой сети production Compose. Произвольный `X-Forwarded-For` игнорируется.

Все Gunicorn workers используют одну таблицу PostgreSQL, созданную миграцией
`accounts.0002`. В таблице хранится HMAC операции и IP, счётчик и срок окна.
На открытии нового окна удаляются до 128 просроченных записей. Лимит Admin
распространяется на попытки входа, поэтому обычная работа сотрудника в уже
открытой сессии его не расходует.
