# Производительность FoodTinder

Production-образ запускает Gunicorn с двумя процессами по два потока
(`gthread`). Это настройка для VM с 2 vCPU, примерно 1,92 GiB RAM и диском
20 GiB. Порядок применения и отката описан в [инструкции развёртывания](deployment.md).

## Исторические измерения

Замеры были сделаны до FT-38. Генератор k6 работал в режиме заданной
интенсивности стартов сценариев. Состав смеси: лента и свайпы 30%, каталог 25%,
рационы 20%, покупки 15%, избранное 7%, аккаунт 3%. Сценарий включает несколько
HTTP-запросов и может не завершиться в пределах окна.

Лимит составлял 192 виртуальных пользователя, а клиентский тайм-аут запроса
составлял 4 секунды. Steady window длилось 120 секунд и исключало прогрев и
завершение уже начатых сценариев после прекращения новых стартов (drain).
В расчёте общего HTTP RPS учитываются ответы для приложения, HTML и ресурсов.
Успешный API RPS считает успешные API-ответы за секунду. Колонка steady window
использует только соответствующий интервал. Целевая интенсивность стартов
сценариев в секунду и полученные HTTP/API RPS измеряют разные величины.
При исчерпании VU часть запланированных стартов может быть пропущена.

| Gunicorn | Сценариев/с | HTTP RPS | Успешный API RPS | Успешный API RPS, steady | Неожиданные ошибки | CPU VM, медиана |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| 1×1 | 8 | 48,42 | 21,86 | 21,07 | 12,36% | 62,87% |
| 2×2, первый прогон | 16 | 76,50 | 41,82 | 41,94 | 6,58% | 99,75% |
| 2×2, второй прогон | 16 | 75,51 | 40,92 | 40,04 | 6,38% | 99,34% |
| 2×4 | 16 | 74,76 | 37,83 | 37,08 | 10,31% | 99,84% |
| 2×4 | 24 | 72,68 | 33,42 | 31,24 | 16,68% | 99,83% |
| 3×1 | 16 | 72,63 | 37,01 | 36,48 | 9,39% | 99,67% |
| 3×2, заявленная настройка | 16 | 67,30 | 29,40 | 27,04 | 16,50% | 99,75% |

Два прогона 2×2 дали в среднем 76,01 HTTP RPS и 41,37 успешных API RPS.
Максимум за одну секунду достигал 149 HTTP RPS, а p95 API при перегрузке
приближался к 4 секундам. Наблюдаемая разница по успешному API RPS с 1×1
составила около +89%. Интенсивность стартов была разной, состояние данных
между прогонами сохранялось, достигался лимит VU, а параметры отдельных
прогонов (особенно 3×2) отдельно не сверялись. Это лучший наблюдавшийся
вариант, без чистого A/B-сравнения или рабочего SLO.

В точках перегрузки ограничением стал CPU VM. Accept queue в `ss -lnt`
показывает TCP-соединения, ожидающие принятия слушателем. Gthread после
`accept()` передаёт работу в пул потоков, у которого своя очередь. Пустая
accept queue совместима с задержками внутри Gunicorn.

## Повторение на выделенном стенде

[Инструкция для k6](../benchmarks/README.md) использует локальный демонстрационный
Compose, синтетических пользователей и текущие запросы каталога. Для сравнения
параметров Gunicorn подготовьте одинаковые начальные данные и интенсивность,
добавьте отдельный прогрев и завершение, повторите каждый вариант и сверяйте
фактическую конфигурацию. Клиентские тайм-ауты видны в k6. Grafana показывает
серверные ответы и время их обработки. Исторические числа не заменяют новый
замер после изменений каталога и мониторинга.

## Объём начального запроса каталога

Сравнение маршрута `/api/v1/recipes/` на 400 активных синтетических записях
в локальном PostgreSQL. Считались байты JSON до HTTP-сжатия, без заголовков
и фотографий. «До» воспроизводит прежний цикл клиента по `next` с лимитом 100.

| Действие | HTTP-запросы | Объём JSON | Карточки в ответах |
| --- | ---: | ---: | ---: |
| До, открытие каталога | 4 | 116 560 Б | 400 |
| После, первая страница | 1 | 8 774 Б | 30 |
| После, первая страница с поиском, приёмом пищи и временем | 1 | 8 833 Б | 30 из 49 совпадений |

Объём начальной загрузки в этом наборе сократился на 92,5%. Каждая следующая
страница запрашивается по действию пользователя.
