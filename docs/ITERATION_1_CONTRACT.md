# FoodTinder — контракт первого командного этапа

Статус: предлагаемый контракт для включения в подготовительный PR перед шестью задачами.
Он описывает будущую реализацию, а не уже существующие endpoints.
Основа проверена 20.09.2026: `master`, commit `3962480c32e2d905788beb38a408b4b9ec600415`.
Источник кода: https://github.com/DeV0id13/food_tinder/tree/3962480c32e2d905788beb38a408b4b9ec600415

Сейчас существуют User, UserProfile, Admin, health и auth/session; остальные четыре
предметных приложения содержат только AppConfig. Frontend прототипа пока отдельный.

## 1. Границы этапа

Результат: пользователь регистрируется/входит, смотрит рецепты, ставит реакции,
добавляет блюда в избранное, вручную собирает рацион на 1/3/7 дней и скачивает покупки.
Данные принадлежат аккаунту и хранятся в PostgreSQL.

В этом этапе нет автозаполнения, drag-and-drop, нейтрального свайпа, undo,
отметок «куплено», калькулятора бюджета и суммарных КБЖУ, редактирования периода уже
созданного плана, переноса localStorage прототипа, капчи и сброса пароля.
Это отложенные требования, а не отмена продукта. Этап не является готовностью
к публичному production-запуску: регистрационные защиты и развёртывание будут отдельной работой.

Сохраняются Django + DRF + PostgreSQL и существующая сессионная аутентификация.
Redis, Taskiq и прочий стек старого приложения к ТЗ в этот этап не входят.

## 2. Общие соглашения API

- Базовый путь `/api/v1/`, завершающий `/` обязателен; JSON, snake_case.
- ID — целые числа существующего Django BigAutoField; фронтенд получает их из API.
- Decimal передаётся строкой с точкой; дата — `YYYY-MM-DD`, datetime — ISO 8601 UTC.
- Коллекции: `{"count": 12, "next": null, "previous": null, "results": [...]}`.
  Локальный DRF LimitOffsetPagination: `limit=30` по умолчанию, максимум 100, `offset=0`.
  Внешний вид этой схемы един для каталога, ленты, избранного и планов; настройки
  пагинации задаются внутри модулей, без правок глобальных settings.
- Ошибки валидации: 400 и стандартный DRF mapping полей/`non_field_errors` к сообщениям.
  Недоступный чужой/несуществующий ресурс — 404. Гость на приватном endpoint — 403
  при текущем SessionAuthentication. Неверные учётные данные — 400 `non_field_errors`.
- Ошибка CSRF — 403; тело может отличаться от DRF JSON. Клиент должен обработать её
  без падения. Не менять глобальный обработчик ошибок только ради единого envelope.
- Все приватные ответы, включая экспорт, исключаются из публичного кеширования.
- `GET auth/session/` остаётся совместимым с текущей реализацией и устанавливает
  CSRF cookie. Небезопасные запросы отправляют актуальный `X-CSRFToken` и session cookie.
  Регистрация, вход и выход тоже требуют CSRF. После входа токен перечитывается.
- Неизвестные поля записи отклоняются 400, включая `user_id`. Прав доступа из JSON не берём.
- Локальное подключение frontend: один origin через прокси `/api/` на Django.
  Dev proxy сохраняет исходный Host (`changeOrigin: false`), чтобы браузерный Origin
  совпадал с Host, который видит Django. Использовать localhost и разрешённый в локальном
  окружении hostname; не отключать CSRF для устранения ошибки проксирования.
  Боевой reverse proxy и публикация — отдельная задача девопса.

## 3. Модели и точки взаимодействия

Это минимальный согласованный набор; служебные timestamps допустимы внутри своего модуля.
Изменение имён и смысла межмодульных полей проходит через интегратора.

### accounts

Существующие `User` и `UserProfile` сохраняются. При регистрации профиль создаётся явно
в одной транзакции с пользователем; для старого пользователя профиль может отсутствовать.
Внешние связи — `settings.AUTH_USER_MODEL`, миграции — `swappable_dependency`.

### catalog

| Модель | Поля/инварианты, нужные другим модулям |
| --- | --- |
| `Ingredient` | `id`, `slug` unique, `name`, `unit`: `g`, `ml`, `pcs` |
| `Recipe` | `id`, `slug` unique, `title`, `description`, `image_url` (может быть пустым), `cooking_time_minutes` > 0, `difficulty` 1–5, `base_servings` > 0, `meal_types`, `steps`, `is_active` |
| `RecipeIngredient` | `recipe` FK CASCADE с `related_name="ingredient_lines"`, `ingredient` FK PROTECT, `quantity` Decimal(12,3) > 0; unique `(recipe, ingredient)` |

`meal_types` — непустой JSON-массив без повторов: `breakfast`, `lunch`, `snack`, `dinner`.
`steps` — непустой JSON-массив непустых строк в порядке приготовления.
Количество каждой строки относится ко всему рецепту на `base_servings` порций.
Единица хранится только у Ingredient; для `pcs` quantity целое.
Ingredient.slug обозначает один продукт в одной канонической единице. Единицу нельзя
менять после появления связанных строк состава; разные рецепты используют тот же Ingredient.

В Recipe также пять необязательных Decimal(10,2), >= 0:
`kcal_per_serving`, `protein_g_per_serving`, `fat_g_per_serving`,
`carbs_g_per_serving`, `estimated_price_rub_per_serving`.
Это справочные значения на одну базовую порцию; неизвестное значение — null.
Они не рассчитываются из состава в этом этапе. Цена приблизительная, валюта RUB.

Публикуемый активный рецепт имеет минимум одну строку состава. Это проверяется сервисом
сохранения/формой Admin с учётом inline, а не только валидатором поля модели.
Редактирование каталога выполняется через Admin; клиентский API только читает его.

### preferences

`UserRecipeState`: user FK CASCADE, recipe FK CASCADE,
`liked_at` nullable datetime, `disliked_until` nullable datetime,
`is_favorite` bool default false; unique `(user, recipe)`.

- `like`: установить liked_at, если ещё не установлен, и снять активный дизлайк.
  Лайк сохраняется после смены суток; повторный запрос не меняет первоначальное время.
- `dislike`: скрыть до следующей полуночи UTC. Старый лайк и избранное сохраняются.
  Истёкший timestamp игнорируется при чтении; job удаления не нужен.
- `favorite=true/false`: менять только избранное. Это не лайк и не дизлайк.
- Лента исключает неактивные рецепты, лайкнутые и рецепты с активным дизлайком.
  Добавление в избранное само по себе не убирает карточку из ленты.
- Записи и ответы ограничены текущим пользователем. Повтор действий не создаёт дубликаты.

Одна функция для planning в `apps/preferences/selectors.py`:
`is_favorite(*, user_id: int, recipe_id: int) -> bool`.
Она только читает собственные состояния. Planning не импортирует views/serializers preferences.

### planning

| Модель | Поля/инварианты |
| --- | --- |
| `MealPlan` | user FK CASCADE, `start_date`, `duration_days` in 1/3/7, `enabled_meals` — непустой JSON-массив meal types без повторов |
| `MealPlanSlot` | plan FK CASCADE с `related_name="slots"`, `day_index` 0..6, `meal_type`, recipe FK PROTECT, `servings` int 1..20; unique `(plan, day_index, meal_type)` |

`day_index=0` соответствует start_date, далее календарные дни. Дополнительно сервер проверяет
`day_index < duration_days` и наличие meal_type в enabled_meals и recipe.meal_types.
Пустой слот представлен отсутствием строки. У одного слота максимум один рецепт.
План не имеет FK на preferences: это состояние доступности выбора, а не часть плана.

Добавлять или заменять рецепт можно только активным рецептом из своего избранного.
Удаление из избранного не удаляет ранее заполненный слот; порции такого слота можно менять.
При изменении только порций сохранённый рецепт повторно не проверяется на избранное/активность.
Планы разных пользователей с одинаковыми датами независимы; несколько планов у пользователя разрешены.
Период, start_date и enabled_meals после создания не изменяются в этом этапе.

Публичная функция `apps/planning/selectors.py`:
`get_plan_for_user(*, user, plan_id: int) -> MealPlan`.
Возвращает только доступный пользователю план, иначе `rest_framework.exceptions.NotFound`.
Shopping использует её и читает `plan.slots`, `slot.recipe.ingredient_lines`, `line.ingredient`.
Оптимизация запросов через select_related/prefetch_related допустима без изменения семантики.

### shopping

Собственных сохраняемых сущностей в этом этапе нет. Источник истины — текущий план и каталог.
Не копировать строки покупок в отдельные таблицы и не записывать данные в planning/catalog.
Снимки состава и цен при создании плана отложены: изменение каталога влияет на последующий расчёт.

Для каждого ингредиента:

`sum(line.quantity × slot.servings / recipe.base_servings)`

Считать через Decimal, группировать по ingredient.id, единицу брать из Ingredient.
Округлять до 3 знаков только после суммирования, ROUND_HALF_UP.
Количество в API и экспортах — десятичная строка с 3 знаками, включая `pcs`;
дробная потребность в штуках допустима после масштабирования (например, `1.500` яйца).
Не округлять её автоматически до упаковки: это отдельная будущая функция.
Порядок строк — ingredient.id по возрастанию, стабильный во всех форматах.

## 4. HTTP-контракт

### FT-01: аккаунты

| Метод и путь относительно /api/v1/ | Вход | Результат |
| --- | --- | --- |
| GET `auth/session/` | — | 200: текущий `{authenticated,id,email}`, id/email null у гостя |
| POST `auth/register/` | `{email,password}` | 201: `{id,email}`; создаёт аккаунт и профиль, автоматически не входит |
| POST `auth/login/` | `{email,password}` | 200: `{authenticated:true,id,email}` и session cookie |
| POST `auth/logout/` | `{}` | 204, завершает сессию; для гостя также 204 при корректном CSRF |
| GET `auth/profile/` | — | 200: поля профиля ниже; при отсутствии записи возвращает пустые значения |
| PATCH `auth/profile/` | подмножество полей профиля | 200: полный профиль; при необходимости явно создаёт запись |

Поля профиля: `date_of_birth` date/null, `gender` из существующих choices или пустая строка,
`height_cm` int/null, `weight_kg` Decimal-string/null. Пустой профиль: null/""/null/null.
Будущая дата рождения недопустима; рост/вес положительны и укладываются в текущие поля модели.
Email и avatar через profile не редактируются; возраст/ИМТ и медицинские поля отложены.
Повторный email без учёта регистра — 400 по полю email. Существующий валидатор пароля
применяется при регистрации; login проверяет пароль, не создаёт новую парольную политику.

### FT-02: каталог

`GET recipes/` — публичная страница RecipeSummary, сортировка id asc.
`GET recipes/<recipe_id>/` — публичный RecipeDetail, 404 для неактивного/несуществующего.

RecipeSummary: `id`, `title`, `image_url`, `cooking_time_minutes`, `difficulty`,
`base_servings`, `meal_types` и все пять справочных полей на порцию из раздела моделей.
RecipeDetail добавляет `description`, `steps`, `ingredients`:

```json
{"ingredient_id": 11, "name": "Рис", "unit": "g", "quantity": "200.000"}
```

Ни slug, ни is_active, ни служебные поля не обязательны в клиентском API.

### FT-03: реакции и лента

| Метод и путь | Вход | Результат |
| --- | --- | --- |
| GET `preferences/feed/` | limit/offset | 200: страница RecipeSummary; публично, для гостя без личных исключений |
| POST `preferences/swipes/` | `{recipe_id, action: "like" или "dislike"}` | 200: RecipeState; нужна сессия |
| PUT `preferences/favorites/<recipe_id>/` | `{is_favorite: true/false}` | 200: RecipeState; нужна сессия |
| GET `preferences/favorites/` | limit/offset | 200: страница активных RecipeSummary текущего пользователя |

RecipeState: `{recipe_id, liked_at, disliked_until, is_favorite}`; временные поля ISO UTC/null.
Обе коллекции сортируются по recipe.id asc. Некорректное action — 400.
Лайк/дизлайк и добавление в избранное неактивного рецепта — 404. Снять избранное
можно и у неактивного существующего рецепта. Несуществующий recipe_id — 404.
Все записи для гостя запрещены; guest dislike в UI может лишь убрать карточку до перезагрузки.
Из-за исключения выбранных рецептов клиент после свайпа обновляет первую страницу ленты,
а не увеличивает offset старой выдачи.

### FT-04: ручной рацион

| Метод и путь | Вход | Результат |
| --- | --- | --- |
| GET `meal-plans/` | limit/offset | 200: страница PlanSummary, сортировка id desc |
| POST `meal-plans/` | `{start_date,duration_days,enabled_meals}` | 201: PlanDetail с пустыми slots |
| GET `meal-plans/<plan_id>/` | — | 200: PlanDetail |
| DELETE `meal-plans/<plan_id>/` | — | 204; удаляет свой план и его слоты |
| PUT `meal-plans/<plan_id>/slots/<day_index>/<meal_type>/` | `{recipe_id,servings}` | 200: Slot; идемпотентно создаёт/заменяет слот |
| DELETE `meal-plans/<plan_id>/slots/<day_index>/<meal_type>/` | — | 204, в том числе для уже пустого допустимого слота |

PlanSummary: `{id,start_date,duration_days,enabled_meals}`.
PlanDetail добавляет `slots`, отсортированные по day_index и порядку breakfast/lunch/snack/dinner.
Slot: `{day_index,meal_type,recipe_id,recipe_title,servings}`.
Невалидный день, выключенный приём пищи, неподходящий рецепт или servings — 400.
Рецепт не из избранного — 400 по recipe_id; неактивный/несуществующий новый рецепт — 404.
Сначала проверяется доступ к плану; данные чужих планов через вложенные endpoints не раскрываются.

### FT-05: покупки

`GET shopping-list/?plan_id=<id>` — приватный ответ:

```json
{
  "plan_id": 7,
  "items": [
    {"ingredient_id": 11, "name": "Рис", "unit": "g", "quantity": "400.000"}
  ]
}
```

`GET shopping-list/export/?plan_id=<id>&file_type=csv|txt` — файл с Content-Disposition attachment.
`file_type` используется вместо конфликтующего с DRF renderer параметра `format`.
Отсутствующий/нецелый plan_id и неизвестный file_type — 400. Чужой план — 404.
Пустой план: 200, items=[], CSV только с заголовком, TXT с сообщением «Список покупок пуст».

CSV: UTF-8 с BOM, разделитель `;`, заголовки `ingredient;quantity;unit`.
TXT: UTF-8, строка `[ ] Рис — 400.000 g` для каждого продукта.
CSV корректно экранирует разделители/кавычки и защищает текстовые ячейки от формул таблиц
(опасный первый значимый символ `=`, `+`, `-`, `@` экранировать префиксом апострофа).
Количество в JSON, CSV и TXT вычисляется одной функцией, а не тремя реализациями.

## 5. Сквозной контрольный пример

Два активных рецепта допускают lunch и dinner. У обоих base_servings=2:

- A: рис 200 g + курица 300 g;
- B: рис 100 g + молоко 200 ml.

Пользователь добавил оба в избранное. В плане на 1 день: lunch=A, servings=3;
dinner=B, servings=2. Покупки: рис `400.000 g`, курица `450.000 g`, молоко `200.000 ml`.
После изменения A до 1 порции: рис `200.000 g`, курица `150.000 g`, молоко `200.000 ml`.
После удаления слота B: рис `100.000 g`, курица `150.000 g`.

Все три формата покупок дают одинаковые количества. Другой пользователь не получает
этот план, слоты и экспорт. После нового входа в другом браузере данные сохраняются.

## 6. Расхождения с прототипом и будущие требования

Frontend первого этапа использует серверные ID и API. localStorage допускается только
для настроек интерфейса, а не как источник рецептов, реакций или планов.
Автовход после регистрации, объединение лайка с избранным и сохранение покупок только
в браузере не добавляются по аналогии с прототипом.

Следующие этапы: гостевой фильтр по ингредиентам, полноценная анкета и ограничения питания,
капча и восстановление доступа, автоподбор из лайкнутых рецептов, drag-and-drop,
суммарные КБЖУ/стоимость, переключение периода без потери данных, отметки покупок,
история/отмена действий, OpenAPI, CI/CD и приватное развёртывание.
