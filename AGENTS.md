# FoodTinder — правила работы в репозитории

## Контекст и источники требований

FoodTinder — десктопное веб-приложение: выбор рецептов свайпами, конструктор рациона,
автоматический список покупок. Работай небольшими законченными изменениями в рамках задачи.

Перед изменениями прочитай текущую задачу, `README.md`, этот файл и локальные
`AGENTS.md` в затрагиваемых каталогах. Для первого командного этапа также прочитай:

- `docs/ITERATION_1_CONTRACT.md` — согласованный контракт моделей, API и поведения;
- `docs/TEAM_TASKS.md` — шесть задач, владельцы файлов и порядок интеграции.

Явное актуальное указание пользователя имеет приоритет. Старый документ с FastAPI
описывает прежнюю архитектуру: не переноси из него технологический стек.
Прототип служит визуальным ориентиром, но не переопределяет согласованные требования.
Если существенное противоречие нельзя разрешить по текущей задаче и этим документам,
опиши его и предложи конкретное решение до изменения публичного контракта.

## Архитектура

- Сохраняй модульный монолит: Python 3.12+, Django, DRF, Django ORM и PostgreSQL 16+.
- Используй версии зависимостей из `[dependency-groups]` в `pyproject.toml`,
  не обновляй их попутно. Установка: `python -m pip install --group dev` или
  `--group prod` (pip >= 25.1). Обе группы включают `base`.
- Сохраняй Django sessions и `SessionAuthentication`; frontend и `/api/` рассчитаны
  на один origin. Не заменяй это JWT и не отключай CSRF ради подключения интерфейса.
- `accounts` владеет пользователями, профилями и аутентификацией.
- `catalog` владеет рецептами, ингредиентами и составом рецептов.
- `preferences` владеет лайками, временными дизлайками, избранным и лентой.
- `planning` владеет планами питания, слотами и порциями.
- `shopping` рассчитывает покупки из плана и отвечает за экспорт.
- Frontend первого этапа находится в `frontend/`.
- Модуль изменяет собственные данные. Разрешены внешние ключи и чтение других модулей
  через согласованные модели/функции; запись в чужие таблицы через обход их логики запрещена.
- Не добавляй Redis, очереди, микросервисы, обязательную асинхронность или универсальные
  repository/service слои без конкретной задачи. Простые операции остаются простыми.
  Сложные расчёты и многошаговые операции выноси в понятные функции своего приложения.
- Общую логику выноси в `common/` только при реальной необходимости и через интегратора.

## Git и границы изменений

- Одна задача — отдельная ветка `feat/ft-XX-short-name`, созданная от актуального `master`
  после подготовительного PR. Старую `feat/stage_one` не используй как общую рабочую ветку.
- Не коммить и не пушь напрямую в `master`. Изменения попадают туда через проверенный PR.
  Не выполняй merge, публикацию или развёртывание без соответствующего поручения.
- Не используй force push, reset чужих изменений или массовое форматирование репозитория.
- До работы проверь `git status` и текущую ветку. Сохраняй незакоммиченные изменения пользователя.
- Меняй только разрешённые пути своей задачи. Чужие модули, миграции и тестовые фикстуры
  не исправляй попутно: укажи владельцу конкретный дефект и требуемый контракт.
- Общие файлы закреплены за одним интегратором из команды: `config/`, `common/`,
  `README.md`, `AGENTS.md`, общие документы, `pyproject.toml`, зависимости, Docker-файлы,
  корневые тесты/`conftest.py`. Изменения в них согласовываются и вносятся последовательно.
- Автор задачи описывает необходимые подключения и настройки в своём документе
  `docs/modules/<module>.md`; интегратор подключает их после готовности модуля.
- CI/CD, workflows и инфраструктурную автоматизацию добавит девопс отдельной задачей.
  В текущие продуктовые задачи их не включай. Локальная проверка своей работы обязательна.

## Данные, безопасность и поведение

- Для связей с пользователем используй `settings.AUTH_USER_MODEL`; не создавай другую
  модель пользователя. Сохраняй вход по email и регистронезависимую уникальность в БД.
- При регистрации вызывай существующие валидаторы пароля; пароль сохраняй стандартными
  средствами Django. Не логируй пароли, cookies, токены и секреты.
- Явно защищай регистрацию и вход от CSRF, включая анонимные POST-запросы.
  После входа учитывай обновление CSRF cookie. Не полагайся только на проверку интерфейса.
- Приватные queryset ограничивай текущим пользователем. Не принимай владельца объекта
  из тела запроса. Проверяй доступ к вложенным ресурсам и экспорту.
- Не ослабляй глобальные permissions: публичный доступ разрешай явно только нужным views.
- Лайк и избранное — разные состояния. Дизлайк первого этапа действует до следующей
  полуночи UTC; нейтрального свайпа нет. Подробности определяет контракт этапа.
- Количества ингредиентов считай через `Decimal`; единица задана ингредиентом.
  Не складывай граммы с миллилитрами и не придумывай коэффициенты пересчёта.
- Изменение моделей сопровождай миграциями только своего приложения.
  Уже слитые миграции не переписывай. Не создавай фиктивные миграции чужих приложений.
- Уникальность и простые инварианты защищай ограничениями БД; проверки пользователя,
  периода и слота выполняй на сервере. Многошаговые изменения делай атомарно.
- `.env`, локальные БД, пользовательские файлы, дампы и секреты не включай в Git.
  Не очищай Docker volumes и не удаляй данные без прямого поручения.

## Проверка и готовность PR

Используй существующие pytest, pytest-django и Ruff. Backend-тесты выполняются с PostgreSQL;
SQLite не заменяет проверку ограничений и миграций. Инструкции окружения — в `README.md`.

Во время разработки запускай тесты своего каталога, например:

```sh
docker compose run --rm web pytest tests/catalog
docker compose run --rm web ruff check apps/catalog tests/catalog
docker compose run --rm web ruff format --check apps/catalog tests/catalog
docker compose run --rm web python manage.py check
docker compose run --rm web python manage.py makemigrations --check --dry-run
```

Подставляй пути своей задачи. Перед принятием интегрированного изменения выполняются
`docker compose run --rm web pytest` и применение миграций в локальном окружении.
Новые frontend-проверки и команды запуска находятся в `frontend/README.md`.

Добавляй содержательные проверки новой бизнес-логики, прав доступа, валидации и регрессий.
Не пиши тесты ради количества. Существующие проверки не удаляй ради зелёного результата.
Не запускай тесты с production credentials.

В PR укажи:

- решённую задачу и получившееся поведение;
- изменённые API/модели, миграции и необходимые интеграционные подключения;
- выполненные команды и результаты; отдельно — что не проверено и почему;
- короткий способ ручной проверки и оставшиеся ограничения.

Если зависимость ещё не слита или окружение недоступно, продолжай независимую часть работы,
но не заявляй о прохождении интеграционных тестов. Не расширяй задачу ради обхода блокера.
